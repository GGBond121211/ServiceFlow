# 03｜AI 系统设计面试题总结

来源：[JavaGuide 原文](https://javaguide.cn/ai/interview-questions/ai-system-design-interview-questions.html)

## 核心视角

AI 系统设计的难点是：模型输出概率化、上下文外部化、工具可能带副作用、依赖会超时、质量不能由 HTTP 状态码证明。因此回答系统设计题应从业务目标和一次请求开始，逐层说明输入、证据、决策、执行、验证、恢复和观测。

## 分层要点

- 入口层：身份、租户、限流、输入校验、请求/Trace ID、敏感数据处理。
- 编排层：同步/流式/异步选择，普通问答、RAG、Agent、人工审批之间的路由。
- 模型层：统一调用、模型路由、Token 预算、Fallback、结构化输出和 Provider 差异。
- 知识与上下文层：RAG、Memory、历史、工具 Schema 的来源、生命周期和权限。
- 执行层：细粒度工具、后端鉴权、确认、幂等、状态查询、补偿和审计。
- 治理层：Prompt/模型/索引版本、评测集、Trace、指标、灰度、回滚和数据留存。

## 高频追问的判断

### 单 Agent 与多 Agent

先缩小工具集合、改善 Schema、用代码路由和上下文隔离；只有当角色拥有明显不同的工具、权限、上下文或验收标准，且单 Agent 失败样本证明分工有收益时才拆多 Agent。多 Agent 要额外处理任务契约、依赖、聚合、超时、部分成功、身份和 Trace。

### 数据库与状态

业务最终状态、流程 checkpoint、缓存、Trace、评测结果是不同对象。涉及订单/退款等写操作时要讨论事务范围、并发、唯一约束、幂等、状态机和不确定结果，不能用“加一个重试”代替一致性设计。

### RAG 与工具

RAG 提供可引用外部证据，工具读取或改变实时业务状态。工具调用要先由模型提出，再由系统校验，不能让模型凭上下文决定权限。高风险写工具需要确认和审计，超时要进入 UNKNOWN 并查询/对账。

### 指标

系统指标包括成功率、P95/P99、TTFT、Token、成本、429、Fallback、工具调用和人工接管；质量指标包括任务完成、最终业务状态、证据忠实度、引用准确、工具选择和参数正确。不同指标要绑定场景与版本，不能用单一平均值或“模型感觉更好”下结论。

## 对 009 的落点

这篇文章可以作为 2.0 的架构检查表，不是当前实现清单。当前 V1 的真实强项是 Python 确定性售后策略、受限工具、数据库状态和 HITL；2.0 如果引入 Java 技术文档，应先决定是学习性旁路、逐步迁移还是新服务，不能因为文章示例使用 Spring Boot 就直接重写现有系统。

## 关键词

生产分层、请求链路、状态/事务、单多 Agent、RAG/Tool 边界、质量指标、回滚。

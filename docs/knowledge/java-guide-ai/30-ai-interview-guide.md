## 四个模块怎么串起来

原文给的因果链，比单纯罗列知识点更值得记：

1. **大模型基础决定一次调用如何运行**。Token 和上下文窗口影响容量与成本，采样参数影响输出波动，Streaming/重试/限流/结构化输出决定后端能否稳定接住模型结果。
2. **RAG 和 Agent 处理两类不同问题**。RAG 从外部知识源检索证据；Agent 根据任务状态决定下一步动作并调用工具。企业知识库、智能客服、数据分析助手通常同时用到二者。
3. **进入真实业务后才需要补治理层**：模型网关、权限、审计、评测、灰度、回滚。

## 按经验选择复习深度

| 经验阶段 | 复习重点 | 回答需要达到的程度 |
|---|---|---|
| 应届、0–1 年 | 大模型基础、RAG 链路、Agent Loop、简单应用架构 | 能解释主要概念，说清一次调用或知识库问答的完整流程 |
| 2–3 年 | API 调用工程、RAG 排查、工具治理、状态与可观测 | 能根据失败现象定位环节，说明方案选择和异常处理 |
| 3 年以上 | 模型网关、成本、安全、评测、灰度、回滚、架构演进 | 能设计完整系统，说明容量、权限、故障恢复、质量验证和演进 |

原文明确：**工作年限只影响追问深度**。简历里写了企业知识库、Agent 平台或 AI 客服，面试官通常会沿着项目继续问数据来源、权限、效果指标、异常处理和上线后维护方式。

## 项目经历常见追问（原文列了 7 条）

- 项目为什么选择当前模型？更换模型需要比较哪些指标？
- RAG 出现召回不到、排序错误或答案不忠实时，分别怎么排查？
- Agent 调错工具、参数不合法或写操作超时时，系统如何处理？
- 如何证明一次 Prompt、模型或检索配置调整带来了改善？
- 模型供应商限流或不可用时，如何排队、降级和切换？
- 知识库和工具调用如何做租户隔离、权限校验与审计？
- 项目上线后记录了哪些质量、成本、延迟和错误指标？

原文的收尾提醒值得照抄：**准备项目经历时优先使用自己项目里的真实约束和处理过程，专题文章中的方案只用于补充原理与备选做法，不要编造并不存在的数据和职责。**

## 对 009 的落点

这篇的复习深度表可以用来判断 009 作品集材料的目标定位。按 `docs/PORTFOLIO.md` 现有内容看，009 已经能覆盖"2–3 年"档的大部分要求（能按失败现象定位环节：`refund_high_rejected_001` 和 `clarify_exchange_order_001` 两个保留失败案例就是现成的分层定位证据），但**"3 年以上"档要求的模型网关、成本归因、灰度和回滚，009 目前没有，也不该为了凑面试档位去实现**（V1 停止边界见 `docs/DEVELOPMENT.md` 第 8 节）。

七条项目追问里，009 当前能拿真实证据正面回答的是第 3、4、7 条：

- **工具调错/参数不合法/超时**：`domain/policies.py` 的确定性判定 + `application/case_service.py` 的副作用收口，模型提议不等于授权。
- **如何证明改动带来改善**：100 案冻结评测 + 数据库终态断言 + 不删失败案例的诚信约束。
- **记录了哪些指标**：最近一次提交 `9e1de9f` 加的 Server-Timing 分阶段埋点（`infrastructure/timing.py`），可拆模型调用、LangGraph、数据库连接、SQL、业务规则、响应组装和 HTTP 往返。

第 1、2、5、6 条（模型选型对比、RAG 排查、供应商限流降级、租户隔离审计）**009 没有真实经历**，按原文要求不应编造。这也正是 `2.0-preparation.md` 里"多供应商""要不要 RAG"等问题待用户确认的原因。

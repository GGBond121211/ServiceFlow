# 25｜LLM/Agent 安全实战

来源：[JavaGuide 原文](https://javaguide.cn/ai/system-design/llm-security.html)

## 威胁模型

Agent 把用户输入、网页/邮件/RAG/图片、工具结果、Memory、MCP/Skill、模型输出和真实业务系统连起来，模型被误导后可能泄露数据、越权查询、重复写入、退款、发信、执行代码或访问内网。直接注入来自用户，间接注入来自外部内容，Jailbreak 以绕过模型安全限制为目标；三者可以叠加。

一次请求要画出保护对象、攻击入口、高风险动作和强制控制点。用户身份、服务端策略和重新鉴权后的结构化业务事实才是受控来源；上传内容、工具结果、Memory、模型输出和第三方描述都按不可信数据处理。Prompt 分隔符和分类器只能降低受骗概率，不能替代后端安全边界。

## 上下文和输出

RAG 必须在召回前按租户、ACL、状态和有效时间过滤；ContextItem 可带 source、tenant、hash、trust、用途和敏感等级，但标签本身不会自动安全。可把“读取外部资料并提取事实”和“决定/执行写动作”拆成两个阶段，并在每个阶段重新校验。

Memory 写入应比普通对话严格：保存来源、写入者、用途、版本、租户、用户和过期；用户偏好、业务事实和可执行指令分开。工具结果不能覆盖系统指令，也不能把异常堆栈、SQL、Token 和内部 URL原样交给模型。

模型输出进入浏览器、SQL、Shell、URL 和文件前要做目标上下文编码、参数化查询、域名/IP/重定向校验、路径规范化和类型限制。Function Calling 的 Schema 只保证形状；金额、订单归属、状态、审批和权限由代码重新判断。

## 工具、审批、幂等与隔离

避免任意 SQL、任意 URL 和通用文件操作，改用 `get_order_summary`、`check_refund_eligibility`、`create_refund_request` 等细粒度动作。按低/中/高风险决定自动执行、草稿/确认、双人审批或禁止自动化；确认必须绑定规范化参数 Hash、用户、租户、资源版本、action 和有效期，参数变化重新审批。

写操作状态要有 PENDING/EXECUTING/SUCCEEDED/FAILED/UNKNOWN；超时进入 UNKNOWN，通过状态查询/对账收敛，不立即重放。代码和浏览器运行环境要非 root、最小 capabilities、seccomp、只读根、最小挂载、默认无外网、资源配额和独立工作区；网络出口拒绝私网、回环、云元数据和未允许重定向。MCP Token 不应透传到下游，scope 要映射到具体能力。

日志和 Trace 默认保存元数据/Hash/版本/策略，完整内容按需脱敏、加密、访问控制和短留存；密钥、密码和长期 Token 不进 Prompt/Trace。供应链要审查模型、依赖、镜像、MCP Server、Skill、工具描述、启动命令、来源、版本、漏洞、禁用和回滚。

## 安全评测与事件响应

安全回归要断言真实副作用：攻击成功率、未授权动作、数据泄露、审批绕过、误拦截、策略延迟和 containment；不能只看模型说“我不能”。覆盖直接/间接、多语言、编码、长上下文、多模态、超时重放、跨租户和伪造工具注解。事件发生后先禁用工具/出口、暂停任务、吊销凭证、保存证据和确认影响，再对账/补偿、修复、清理污染、加入回归集并恢复。

## 对 009 的落点

当前 V1 是模拟业务，但退款审批路径正好适合作为 2.0 安全契约案例：模型提议 ≠ 权限，策略/工具/DB 状态要分开，审批恢复要绑定本次动作。没有真实外部支付和网络工具前，不应虚构生产安全能力；可以先用模拟副作用和确定性断言做回归。

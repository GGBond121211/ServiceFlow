# ServiceFlow 2.0 预备边界与决策台账

状态：初始化完成，待用户确认 2.0 产品目标。本文是决策入口，不是已实现功能说明。

## 目标

把 JavaGuide AI 资料转成 ServiceFlow 2.0 可以逐项验证的设计候选，保持以下边界：

- 先从当前 V1 的真实行为、源码和测试出发。
- 每个新增能力都要回答“解决哪个具体用户/业务问题、用什么证据验收、带来什么成本和风险”。
- 外部资料提供候选模式，不直接决定技术栈；项目的实现事实只由源码、测试和项目文档确认。
- 2.0 的改动应尽量形成清晰的阶段，而不是一次性把 RAG、Memory、MCP、多 Agent、Gateway、语音和生产安全全部引入。

## 已知基线

ServiceFlow 当前 V1 是模拟电商售后单 Agent。主链路可以概括为：

```text
用户自然语言
  -> 结构化意图
  -> Python 确定性策略
  -> 受限业务工具
  -> 数据库事实与状态
  -> 可验证响应 / 必要时人工审批
```

现有项目文档已经明确的事实优先级高于本目录：源码和测试 > `README.md`、`docs/LEARNING_STATE.md`、`docs/DEVELOPMENT.md`、`docs/PORTFOLIO.md`、`docs/USER_FLOW.md` > 本外部资料笔记。任何设计讨论都要明确是在“当前实现”“历史实验”“未来候选”还是“尚未验证”。

## 候选能力池，不代表承诺

以下内容来自 32 篇资料的交叉归纳，暂时只作为候选池：

### A. 接口和领域边界

- 将入口请求标准化为包含 `request_id`、用户/租户边界、场景、输入、变量和权限范围的内部任务对象。
- 将同步生成、流式事件、人工暂停/恢复和异步任务分别表达，避免调用方猜测“什么时候才算完成”。
- 将 `ModelGateway`、`ContextAssembler`、`RagService`、`EvaluationService` 这类职责作为接口讨论对象，但不提前把每个接口变成独立服务。
- 工具使用“模型提议、后端执行”的边界：结构校验、业务语义、资源鉴权、风险策略、确认、幂等、审计和结果验证都不能由模型替代。

### B. Workflow / Agent / Loop

- 当前 LangGraph 流程可以用 `State`、节点职责、条件边、人工中断和恢复语义来继续梳理。
- Loop 必须同时定义继续条件、退出条件和最大轮次/时间/Token/工具次数等安全边界。
- 只有存在可观察验收信号时才考虑外层 Loop；第一版可从只读诊断/回放开始，逐级开放修改权限。
- 多 Agent 只在角色、工具、上下文、权限和交付物明显分离且单 Agent 失败证据充分时考虑。

### C. RAG / Knowledge Base

- 若 2.0 有真实知识问答目标，先做解析、标题/表格/页码保真、Metadata、权限、引用和最小评测集。
- 先用可解释的混合检索、RRF、重排和上下文裁剪建立基线；没有多跳/全局归纳失败，不先引入 GraphRAG。
- 文档、Chunk、Embedding、索引、权限和删除要版本化；增量更新、全量重建、别名切换、补偿和回滚是同一个生命周期问题。
- 向量数据库选型应由数据规模、过滤比例、QPS、延迟、召回和现有技术栈评测决定；不能把外部示例的 PostgreSQL/pgvector 直接套到当前 MySQL 项目。

### D. Gateway / Observability / Security

- 第一阶段若只需统一 Provider、超时、错误转换、usage 和基础日志，应用内轻量模块可能足够；独立 Gateway 需要真实复用、配额或治理需求驱动。
- Trace 要记录模型、Prompt 版本、RAG 命中、工具调用、Token、TTFT/总延迟、重试和最终业务状态；完整原文按脱敏、权限和保留期控制。
- Metrics 发现整体异常，Logs 记录事件，Trace 还原执行，Evaluation 判断质量，Audit 追责高风险操作；不能混成一张“成功/失败”表。
- Prompt Injection 防护不能只靠 Prompt。外部内容、模型输出、工具结果、Memory 和第三方组件都按不可信数据处理；真正的边界由最小权限、鉴权、审批、沙箱、网络出口、幂等和审计建立。

### E. 语音

- 只有明确语音产品目标时再引入。语音链路需要 VAD、ASR、LLM、TTS、播放队列、取消/打断和会话状态协同。
- 级联链路更容易审计和替换组件；原生 Realtime 可能降低延迟但更黑盒。选择依据应是首段延迟、端到端 P95/P99、打断、合规、成本和可观测性，而不是“更先进”。

## 推荐的阶段闸门

下面是候选顺序，不是已批准计划：

1. **目标与基线**：明确用户流程、非目标、成功指标，跑通 V1 回归并保存当前行为。
2. **契约与可观测**：先定义请求/状态/工具/错误/结果的最小契约，补足能解释一次任务的 Trace 或结构化运行记录。
3. **一条核心业务增量**：只选一个高价值路径，用确定性状态和测试证明收益。
4. **知识/检索增量（如确有目标）**：从小规模、可引用、可权限过滤的基线开始，评测后再扩大。
5. **可靠性与安全增量**：按真实副作用补幂等、UNKNOWN、审批、对账和安全回归。
6. **规模化能力（如确有证据）**：再评估 Gateway、队列、Memory、Multi-Agent、GraphRAG、独立服务或语音。

每一阶段都应保留：目标、范围、方案、替代方案、风险、验收命令/测试、结果、回滚方式和“未做什么”。

## 资料使用规则

- 文章中的数字阈值（如 Chunk 大小、Loop 次数、采样比例、告警线、延迟目标）只能作为实验起点，必须在 009 的数据和场景上重新测量。
- 文章里的 Java/Spring AI 代码是概念示例，不代表当前 Python/LangGraph 代码可以直接替换，也不代表示例 API 在当前依赖版本中存在。
- 文章提到的产品、协议、模型、价格、版本和许可证都是可能变化的外部事实；真正实施前要核对官方文档、当前依赖和本地环境。
- 任何外部链接、文档、模型输出、工具结果和用户上传内容都按不可信数据处理；它们不能覆盖项目治理规则或用户明确授权边界。

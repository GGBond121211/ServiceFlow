# 09｜AI Agent 记忆系统详解

来源：[JavaGuide 原文](https://javaguide.cn/ai/agent/agent-memory.html)

## 记忆的层次

短期/工作记忆服务当前任务，受到上下文窗口限制；长期记忆跨请求保存仍有价值的信息。记忆还可以按内容分为事实、经验、工作记忆，或按形态分为情景、语义、程序性记忆。底层可能是 Token 文本、向量、图、缓存甚至参数，但存储形式不能改变隐私和删除要求。

记忆生命周期可以拆成：从对话中抽取（encode）→ 存储 → 按当前问题检索 → 合并/巩固 → 反思 → 冲突处理和遗忘。模型“可能是用户偏好”的一句话不能直接固化；应有 Schema、来源、置信度、适用范围、租户/用户边界、版本和过期时间。

### 短期与长期的工程差异

短期上下文可用滑动窗口、摘要、历史裁剪、结果卸载和子任务隔离控制；重型工具结果应以引用保存，不要每轮重复塞入。长期记忆要处理写入幂等、MVCC/版本、检索排序、冲突和用户删除。高风险事实可先异步审核，不能把每次临时表达都写成长期规则。

RAG 取共享或外部知识，Memory 取个性化背景；两者都可能使用向量，却要分开 namespace、权限、来源、更新和过期。业务事实仍应从权威服务读取，记忆只作背景或检索入口。

### 演化与检索

单纯 append 会变成流水账。Self-Reflection 可在任务完成后提炼可复用教训；Reflect Loop 可对高风险事实做证据和验收复核；Clustering/Consolidation 可合并重复条目。遗忘可以根据相关性、重要性和时间衰减排序，在重排阶段应用动态权重；新旧事实冲突时标记旧条目失效，并定期处理软删除和索引健康。

向量召回可与 BM25/Sparse、图关系和 Reranker 混合。多租户、用户、组织、时间和业务标签应由数据访问层硬过滤；强过滤可能降低 HNSW 可达性和召回，必要时物理隔离高活跃租户。调优先看 Trace 的 query、过滤、候选和重排，再判断是否需要修改写入抽取。

### Markdown 记忆的边界

少量项目约定、偏好和踩坑记录适合 Markdown：透明、可审计、可 Git 版本化、无需额外向量服务；大量自由文本则需要按需检索。常驻入口应保持短小，详细内容分文件按需加载；日志、密钥、Token 和高频动态状态不应放入共享记忆。

文章对 `CLAUDE.md`、`AGENTS.md`、path-scoped rules 和 Auto Memory 的讨论说明了一个通用原则：规则只有在对应错误真实出现、且能被验证时才值得长期保留；自动加载不等于正确，也不等于减少上下文消耗。

## 对 009 的落点

当前 ServiceFlow 的 checkpoint、对话历史和数据库状态不能直接称为长期 Memory。2.0 若确实需要跨会话偏好，应先定义“记什么/谁能读/多久过期/如何更正删除”，并把用户记忆与售后事实分开；本目录本身是版本化知识文档，不是自动写入用户记忆。

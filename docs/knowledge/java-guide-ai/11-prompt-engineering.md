# 11｜提示词工程实战指南

来源：[JavaGuide 原文](https://javaguide.cn/ai/agent/prompt-engineering.html)

## Prompt 的职责

Prompt 不是越长越好，而是要把角色、目标、约束、输入上下文、输出格式和失败处理说清楚。Zero-shot、Few-shot、任务分解和结构化输出是工具，不是固定配方；示例需要覆盖正常、边界和拒答，且不能污染真实证据。

长文本处理时，先把用户问题和输出目标写清，再把资料作为受标记的证据；关键约束和重要证据不要无序埋在上下文中间。引用、字段、枚举和未知值需要可机械检查的格式，能用供应商原生 Schema 就不要只靠自然语言要求 JSON。

思维链不应被当作安全或正确性的证明。模型自述的理由可能不完整或事后合理化；高风险结论要依赖业务规则、来源和结果校验。Best-of-N、Self-Consistency 等方法能改善部分生成任务，但会增加成本，必须用固定评测集验证。

## 注入与安全

直接 Prompt Injection 来自用户，间接注入来自网页、邮件、RAG、图片、工具结果或 Memory。分隔符、XML、指令优先级和检测器能帮助模型识别边界，但 Prompt 不是权限边界。工具白名单、后端鉴权、敏感数据最小化、审批、网络/文件沙箱才负责限制实际副作用。

外部资料应该只作为“待分析数据”；不能因为文档里写了“忽略规则”就让它改变系统指令、工具名、租户或授权范围。模型输出进入浏览器、SQL、Shell 或下游 API 前仍要按不可信数据处理。

## 对 009 的落点

V1 的意图提取 Prompt 应保持小而明确，并用 Pydantic 解析和业务策略做后置校验。2.0 若要改 Prompt，应记录版本、输入变量、模型、评测集和失败样本；不要把文章示例中的高强度指令直接写进项目治理文件，也不要用 Prompt 代替退款规则。

## 关键词

Zero-shot、Few-shot、任务分解、结构化输出、证据边界、Lost in the Middle、Prompt Injection、Jailbreak、可验证 Prompt。

# 15｜Harness Engineering

来源：[JavaGuide 原文](https://javaguide.cn/ai/agent/harness-engineering.html)

## 核心观点

可以把 Agent 看成 `Model + Harness`。模型负责推理和生成；Harness 负责系统提示、工具、文件系统、沙箱、编排、反馈、约束、状态、验证和恢复。一个模型即使能力不变，只替换文件编辑接口、错误反馈或测试闭环，任务完成率也可能明显变化。因此 Agent 不稳定时，先查工具接口、执行环境、结果可读性、状态持久化和验证机制，不要只换模型或加 Prompt。

### 三种工程层次

- Prompt Engineering：如何把局部指令说清。
- Context Engineering：本轮给模型看哪些必要信息。
- Harness Engineering：系统如何持续执行、验证、纠偏、观测和恢复。

文中还用六层作为检查框架：信息边界、工具系统、执行编排、记忆/状态、评估/观测、约束/校验/恢复。它是分析框架，不是统一协议；早期可以先补信息边界和错误拦截，再按真实需求增加状态、编排和观测。

## 关键实践

工具应使模型能够表达正确动作，失败输出应包含下一步可执行信息。上下文越多不一定越好；文中提到的约 40% Smart/Dumb Zone 只是特定观察，不是通用阈值，项目要用自己的回放决定何时压缩、分段或交接。目录式项目规则、局部 Linter、结构测试、进度文件、端到端验证和后台清理都属于 Harness，而不是一份超级 `AGENTS.md`。

文中 P0 是建立短入口规则、机械化检查和仓库事实来源；P1 是分层上下文、进度追踪和端到端验证；P2 才是专业化 Agent、垃圾回收和更完整可观测。能力等级从无约束、基础规则、反馈回路、专业化到无人值守自治，不能跳过可验证基础。

## 案例和边界

OpenAI 案例强调目录式文档、架构 Linter、可观察的执行环境和定期清理；Anthropic 案例强调并行专业 Agent、测试切分、自我评估独立化和 context reset；Stripe Minions 强调“确定性步骤由状态机执行、灵活步骤交给 Agent”、受筛选的工具集合和 CI 回路；Mitchell Hashimoto 则强调单 Agent、每个失败沉淀为规则和人工深度参与。它们的投入和数字不能直接外推到 009。

未解决问题包括棕地改造、AI 生成测试的独立正确性、生成代码的长期维护、Harness 的厚薄以及单多 Agent 取舍。架构检查和清理不能证明用户流程正确，仍需要独立业务测试。

## 对 009 的落点

009 的 `README`、学习状态、测试、LangGraph 状态和确定性策略已经是 Harness 的原材料，但本目录不会自动创建一个新的 Agent 控制层。2.0 可以先把高频失败转为可执行检查、补充回放和状态边界；只有出现真实重复错误，才新增规则或工具。

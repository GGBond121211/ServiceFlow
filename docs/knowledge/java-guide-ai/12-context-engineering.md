# 12｜上下文工程实战指南

来源：[JavaGuide 原文](https://javaguide.cn/ai/agent/context-engineering.html)

## 定义与问题

Prompt Engineering 主要问“怎么说”，Context Engineering 主要问“在这一轮给 Agent 看什么、何时给、以什么结构给”。Context 可包含系统规则、用户输入、历史、RAG、Memory、工具定义/结果、计划、错误、评测和摘要。上下文窗口不是无限记忆；材料越多可能出现 Context Rot、Lost in the Middle、成本和延迟上涨。

目标不是把所有材料放入模型，而是最大化与当前决策有关的信噪比。静态规则应明确角色、权限、流程和格式；动态数据应只注入本次任务所需内容；工具列表应按场景裁剪；Few-shot 示例应少量且代表边界；历史可以滑动窗口、摘要或外部引用。

## 组装策略

可将 `ContextAssembler` 的输入理解为目标、约束、当前证据、记忆、候选工具和历史。先做硬过滤（租户、权限、时间、版本），再做相关性排序、去重、相邻片段合并和 Token 预算裁剪；RAG、Memory、工具结果要标注不同来源、可信度和用途，不能拼成无标签背景。

长任务还需要外部进度文件、结构化交接、子 Agent 隔离和必要时 context reset。压缩要保留当前目标、已确认事实、未完成事项、失败原因、引用 ID 和下一步；不要把精确金额、错误码或资源版本在摘要中洗掉。JIT retrieval 比一开始全量加载更能控制窗口，但要保留可重放的检索记录。

## 测量和回放

应记录实际每一轮的 context 组成、Token、截断、排序和工具集合，而不只记录模板。评测至少覆盖答案质量、工具选择、引用、延迟、成本、上下文利用率和拒答。具体的 40% 等观察值只能作为实验假设，不能作为通用告警线。

## 对 009 的落点

ServiceFlow 当前的上下文主要是用户输入、结构化意图、历史/状态、策略结果和工具返回。若 2.0 接入政策知识库或更多工具，应先把“业务事实、文档证据、模型建议、流程状态”分区，再用现有策略和数据库做最终判断，而不是扩大一个超级 Prompt。

## 关键词

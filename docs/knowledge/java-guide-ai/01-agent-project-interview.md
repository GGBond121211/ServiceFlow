# 01｜Agent 项目面试实战

来源：[JavaGuide 原文](https://javaguide.cn/ai/interview-questions/agent-project-interview-guide.html)

## 文章要解决的问题

这篇文章不是教人背“用了什么框架”，而是教人把 Agent 项目讲成一条可核验的工程链。面试官真正关心的是：在什么约束下做了什么选择，替代方案是什么，解决了什么问题，又引入了什么成本；最后能否用测试、Trace、评测结果或失败案例证明判断。

## 结构化笔记

### 项目叙述框架

一份可信的项目说明至少要交代业务问题、成功标准、输入和输出、外部副作用、原方案、个人负责范围、约束、关键取舍、质量证据和失败边界。30 秒版本讲目标、主链路和个人贡献；3 分钟版本再展开一次请求如何进入系统、何处使用模型、何处由代码和数据库控制，以及一次 Badcase 如何定位和修复。

### 一次请求的七个逻辑层

1. 入口：认证、租户、限流、请求/运行 ID、输入大小和数据预处理。
2. 编排：判断信息是否完整，选择问答、RAG、工具、人工审批或异步路径。
3. 模型：负责语言理解、分类、规划或结构化提议，不直接拥有业务权限。
4. 上下文：管理历史、RAG、Memory、工具 Schema、版本和 Token 预算。
5. 工具：提供细粒度业务动作，做参数、权限、风险、幂等和结果校验。
6. 状态：保存当前任务、审批、重试、业务快照和可恢复位置。
7. 治理：观测、评测、审计、成本、版本、灰度、回滚和数据留存。

这些是逻辑职责，不要求一开始拆成七个微服务。Agent 和 Workflow 的边界也不是二选一：认证、确认、写入和审计适合确定性流程；需要根据证据选择下一步的部分才交给 Agent。

### Agent、RAG、Memory、Context、State 的区分

- RAG 是从外部知识源取证。
- Memory 是跨会话保留的个性化事实、偏好或经验。
- Context 是本次模型调用实际看到的材料。
- State 是当前任务推进所需的输入、步骤、审批、工具结果和业务状态。

Checkpoint 只能帮助流程恢复，不能替代订单数据库；Memory 也不能替代权威业务事实。Function Calling 是模型提出结构化动作，MCP 是 Host/Client/Server 之间的工具与上下文协议，Agent 则是根据观察决定下一动作的运行机制。

### 工具与失败处理

工具 Schema 只约束形状，不能证明资源属于当前用户，也不能证明金额符合业务规则。执行前需要重新读取权威状态、做资源级鉴权和风险判定，高风险动作绑定本次参数的确认凭证。

网络超时不能简单归类为失败：下游可能已成功。写操作要用稳定 `actionId`/幂等键、状态查询和对账；有限重试要有 deadline 和预算。人工中断要保存 run、checkpoint、待审批动作和版本，恢复后重新校验权限与业务状态。

### 评测与 Badcase

Badcase 的建议流程是：保存输入和 Trace → 写清期望/实际 → 按入口、模型、检索、工具、状态、环境分层假设 → 一次只改一个变量 → 找根因 → 在正确层修复 → 将原样本加入回归集。Trace 至少应能关联 request/run、版本、模型、检索文档、tool call、重试/幂等、checkpoint、结果、成本和延迟；不默认保存私密 CoT，敏感原文需要脱敏和受控留存。

## 对 009 的落点

当前 ServiceFlow 应继续按“受约束的 Agentic Workflow/Reflection Loop”描述：模型提议意图，Python 策略决定是否允许，工具改变模拟业务状态，数据库状态是最终事实，人工审批是暂停/恢复路径。面试材料中应明确当前是模拟电商售后 V1，不能把未来的 RAG、Redis、真实支付、生产鉴权或多 Agent 说成已实现。

项目事实边界、Agentic Workflow、Hybrid、工具安全、UNKNOWN、幂等、HITL、Trace、Badcase、可验证结果。

# ServiceFlow 能力边界与真实性声明

最后更新：2026-09-04。本文与 [`ARCHITECTURE.md`](ARCHITECTURE.md)、[`EVALUATION.md`](EVALUATION.md) 同为对外说明。

本项目是**工程学习与本地演示项目**，不是生产系统。本文明确区分四种状态，公开说明必须落在其中之一，不得含糊。

## 一、状态分类

| 状态 | 含义 |
| --- | --- |
| ✅ **已实现且可复现** | 代码在仓库里，有测试或评测产物，按文档命令可复现 |
| 📊 **历史实验** | 特定时间、特定配置下跑过一次，结论只在该条件下成立 |
| 🧪 **仅用于演示的模拟实现** | 用 Fake / 模拟数据证明接口与故障行为，不接真实外部系统 |
| 📝 **评估过但未实施** | 做过取舍分析并有书面理由，**没有实现，不得声称做过** |

## 二、全部为模拟的内容

项目中的**用户、订单、商品、金额、物流状态、售后政策、审批人和处理结果，全部是自建模拟数据**。

- 不接真实支付、真实物流、真实客服 SaaS 或任何真实客户数据。
- 外部服务（物流、退款、补偿、工单）由 Provider Adapter + Fake Provider 实现，用途是**证明适配器契约和故障处理路径**（超时、429、5xx、PENDING、UNKNOWN），不代表接入过真实生产业务。
- 政策阈值（7 天退款期、¥500 审批线、30 天换货期）是本项目自定义的模拟规则，不来自任何真实商家。

## 三、V1（当前已冻结基线）不包含什么

V1 冻结于 `v1.0.1`（`c7d61fd`）。它**不包含**：登录与身份认证、权限系统、风控、重试、缓存、消息队列、Kubernetes、多 Agent、向量数据库、复杂 RAG、生产安全防护、高可用。

V1 的评测结果见 [`EVALUATION.md`](EVALUATION.md) 的「V1 冻结基线」一节，其性质是：📊 **历史实验**——自建模拟数据、本地单次运行、真实模型 API。**不是生产 SLA，不是线上流量表现，不是人工语义评分。**

## 四、本地演示 ≠ 生产能力

当前 2.0 已实现本地模拟的租户/订单范围校验、确认、金额审批、Answerability Gate、PII 脱敏、人工接管队列和 SQL 恢复。这里的用户、租户、审批主体和客服队列仍是演示数据与本地角色，**不等于真实认证系统、企业 IAM、生产审批链或真实客服 SaaS**。

Provider `UNKNOWN` 当前不会重新执行副作用：可由 Fake Provider query、去重 Webhook 或人工对账推进。Webhook Inbox、事务 Outbox、SQL TaskEnvelope 和 Celery/Redis Outbox Worker 已实现；Provider reconcile 的周期调度、真实 Provider、真实外部通知和 SSE 尚未实现。

LLM Gateway 已实现本地双副本、服务 Bearer 鉴权、真实 tenant 限流、独立模型审计和每副本内存 Metrics。两个模型仍共享 Frontier Base URL 与凭据，不能称独立 Provider 容灾；本地服务密钥也不等于企业 IAM。Streaming 当前明确返回 422，Prometheus/Grafana、Jaeger/Collector 和尾部采样尚未实现。

2.0 引入的运维组件仅用于本地可复现演示，**不得表述为生产能力**：

| 项目中的做法 | 不能说成 |
| --- | --- |
| Docker Compose 本地编排 | 生产部署 |
| 两个网关副本 + 反向代理 | 生产级高可用 / 多机房容灾 |
| kind / Minikube 本地集群 | 云端 Kubernetes 生产集群 |
| 故障注入（停 Redis、停副本、Fake Provider 报错） | 真实线上故障处理经验 |
| 离线评测与压力测试 | 线上真实流量指标 / SLO |
| Fake Provider 的成功率 | 真实供应商的可用性 |
| Worker 停机入队、重启消费的一次 smoke | 生产消息队列高可用、吞吐或 exactly-once 保证 |

## 五、评估过但未实施的技术

以下技术**有取舍分析，但没有实现**。公开说明中只能说"评估后决定不做，理由是……"，**不得表述为做过**：

| 技术 | 不做的理由（摘要） |
| --- | --- |
| 模型微调（SFT） | 政策会随业务变更，微调把规则烧进权重后无法版本化回滚；瓶颈在多轮状态合并而非语言理解；可用标注量远达不到有意义规模 |
| LoRA / 全量微调对比 | 同上。仅作为取舍分析记录（可训练参数量、显存、多 adapter 切换、灾难性遗忘风险、回滚成本） |
| 量化 / vLLM / 自建推理 | 无 GPU，模型走 API；实测分阶段延迟显示瓶颈在模型调用与多轮工具循环，不在推理吞吐 |
| GraphRAG | 售后政策是版本 / 时间 / 范围约束，不是需要多跳关系遍历的知识图谱 |
| 多 Agent / A2A | 无失败证据表明单 Agent 不够；工具与政策边界集中，拆分只会增加状态一致性成本 |
| 语音（ASR / TTS / VAD） | 交互形态确定为会话多轮 + SSE，无语音产品目标 |
| SLI / SLO 与告警 | 无线上流量可建立基线，定 SLO 只会是编造数字 |

## 六、评测诚信约束

- **不删除失败案例，不修改期望答案来提高成绩。** V1 保留的 5 个失败案例见 [`EVALUATION.md`](EVALUATION.md)。
- 报告数字必须标注配置来源：Fake Model / 异步回放模型 / 真实模型 API 是三件不同的事，不能混引。
- 安全类结论必须**双向报告**：只报"违规降为 0"而不报误拦截率的结论无效——把所有请求都拒绝也能让违规归零。
- 借鉴外部评测方法论（如用例契约结构、`pass^k` 指标口径）时会显式署名来源；**未运行对方 harness 就不会声称"在某 benchmark 上取得 X 分"**。公开案例均为仓库内自建的模拟案例。

## 七、这个项目适合证明什么

适合证明：把业务问题拆成入口 / 编排 / 执行 / 持久化 / 运营五层的能力；让模型自主使用工具同时由代码守住权限与金额的边界设计；对 RAG / Memory / Tool 三类上下文生命周期的理解；用评测、Trace 和实验定位并修复 Bad Case 的方法；Linux / 容器 / CI-CD 的基本工程实践。

不适合证明：真实生产系统的运维经验、大规模流量下的性能调优、真实支付与资金安全、模型训练与推理优化。

# 工程边界与非目标

## 1. 项目性质

ServiceFlow 是大三学生的 Agent 工程作品集，所有业务数据和规则都是本地模拟。项目没有真实消费者、资金、隐私数据、支付接口和线上流量。

因此工程重点是可运行的业务闭环、数据库状态、Agent 工具调用和量化评测，不以生产级防御或安全体系为目标。

## 2. 明确不实现的内容

### 生产安全与账号体系

- 用户注册、登录和密码；
- JWT、OAuth、Session 鉴权；
- 角色权限、资源授权和多租户；
- 风控、合规、隐私治理和数据脱敏系统；
- API 网关、限流、WAF 和密钥管理平台。

### 安全专项代码和测试

- Prompt 注入检测或过滤；
- 恶意输入识别；
- 越权攻击和数据窃取模拟；
- SQL 注入、XSS、CSRF 等专项测试；
- 漏洞扫描、依赖安全扫描和渗透测试；
- 安全红队、对抗数据集和安全评分。

### 防御性和生产可靠性机制

- 自动重试和指数退避；
- 熔断、降级、限流和服务发现；
- Redis 缓存和消息队列；
- 幂等键平台和分布式锁；
- 自动恢复、灾备和数据备份体系；
- Kubernetes、微服务和多区域部署；
- 为未来实现预留的接口、工厂、兼容层和配置层。

### 与核心作品集无关的扩展

- 多 Agent 协同；
- 向量数据库和复杂 RAG；
- 知识图谱；
- 模型微调、强化学习和训练平台；
- 真实外部商城、支付或物流接入；
- 多模态和语音客服。

## 3. 必须保留的普通业务代码

下列内容不是安全加固，而是产品本身的正确性，因此需要实现和测试：

- 订单是否存在；
- 订单当前状态；
- 签收时间是否满足项目规则；
- 金额是否进入人工审批分支；
- 是否缺少订单号和诉求；
- 状态变更是否符合本文定义的有限状态模型；
- 数据库写入后最终状态是否与处理结果一致；
- API 输入是否满足 Pydantic 结构化契约。

基础错误处理只需要返回清楚的项目内错误，例如 `order_not_found`、`missing_order_id`、`action_not_supported`。不为理论故障增加恢复流程。

## 4. 测试边界

允许并要求：

- 领域规则单元测试；
- 仓储和数据库集成测试；
- FastAPI 业务接口测试；
- LangGraph 节点和端到端测试；
- Agent 固定任务评测；
- 已经发生的真实回归测试。

明确禁止纳入 V1：

- 安全测试；
- 攻击或恶意输入测试；
- 高并发、压力和容量测试；
- 容灾和故障注入测试；
- 为追求覆盖率而生成的低价值测试。

## 5. 人工审批的定位

高金额退款进入人工审批，是为了展示 LangGraph 中断和恢复，以及普通业务工作流，不是为了声称项目具备生产风控能力。

## 6. 变更边界

若后续希望加入真实外部系统、账号、公开部署或真实用户数据，应视为新的项目阶段，重新定义风险等级和边界。V1 实施过程中不能以“未来可能需要”为理由提前加入这些内容。

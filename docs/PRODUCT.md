# 产品定义

## 1. 一句话定义

ServiceFlow 是一个面向模拟电商订单的售后工单 Agent：它理解用户请求、查询订单、匹配项目内售后规则、调用业务工具，并返回带最终状态的处理结果。

## 2. 目标用户

唯一目标用户是希望在本地演示售后流程的项目体验者。项目不区分消费者、客服、主管等真实角色，也不建设账号系统。

## 3. V1 输入

- 一个固定模拟用户 ID，由演示页面选择；
- 一段自然语言售后请求；
- 可选订单号；
- 对审批节点的“同意”或“拒绝”操作。

示例：

```text
我是 USER-001。ORDER-001 还没发货，帮我取消。
ORDER-003 的耳机有质量问题，我想退款。
我买的键盘按键失灵，但是忘记订单号了。
```

## 4. V1 输出

- Agent 的简短回复；
- 识别出的意图和订单号；
- 匹配到的业务规则 ID；
- 已调用的工具及结构化结果；
- 当前订单、退款、工单或审批状态；
- 若信息不足，返回一个明确的补充问题。

完整输入输出示例、决策图和审批时序见 `docs/USER_FLOW.md`。

## 5. 核心用户故事

### US-01 查询订单

用户提供订单号后，系统返回商品、金额、时间和状态，并为后续决策提供结构化数据。

### US-02 取消未发货订单

已支付但未发货的订单可以被取消，最终状态写入数据库。

### US-03 七天内普通退款

签收不超过七天的普通商品可以进入模拟退款流程。

### US-04 质量问题换货或维修

签收不超过三十天且描述为质量问题时，可以创建换货工单；超过期限时创建普通人工工单。

### US-05 高金额人工审批

退款金额大于 500 元时，系统先创建待审批记录；演示者批准后才能继续模拟退款。

### US-06 信息不足

缺少订单号或处理诉求时，Agent 只询问完成任务所需的信息，不执行状态变更。

### US-07 查询处理结果

用户可以查询已经创建的退款、工单或审批状态。

## 6. V1 模拟业务规则

这些规则只属于本项目，不代表任何真实企业或法律政策：

| 规则 ID | 条件 | 结果 |
|---|---|---|
| `POL-QUERY-01` | 用户只查询订单或处理状态 | 返回当前信息，不改变业务状态 |
| `POL-CANCEL-01` | 订单状态为 `paid` | 允许取消，状态变为 `cancelled` |
| `POL-REFUND-01` | 普通商品已签收且不超过 7 天 | 允许模拟退款 |
| `POL-EXCHANGE-01` | 质量问题且签收不超过 30 天 | 创建换货工单 |
| `POL-TICKET-01` | 无法直接处理或超过期限 | 创建普通人工工单 |
| `POL-APPROVAL-01` | 模拟退款金额大于 500 元 | 先创建待审批记录 |
| `POL-INFO-01` | 缺少订单号或关键诉求 | 询问缺失信息 |

## 7. 状态模型

### Order

```text
paid -> cancelled
shipped -> delivered
delivered -> refunded
delivered -> ticket_open
```

项目只实现评测案例需要的状态转移，不建设完整订单生命周期。

### Approval

```text
pending -> approved
pending -> rejected
```

### Ticket

```text
open -> resolved
```

V1 演示创建和查询工单，不实现复杂客服处理后台。

## 8. V1 成功标准

- 三条代表流程可从浏览器端到端完成：取消、直接退款、审批后退款；
- 信息不足时能够继续询问并恢复同一会话；
- 最终业务状态可通过 API 和数据库核验；
- 100 个固定 Agent 案例可以自动执行并生成总体、核心40案和复杂中文60案报告；
- Docker Compose 可启动 API 与 MySQL；
- 项目说明能够诚实区分模拟数据、规划目标和真实结果。

## 9. 非目标

- 真实客服话术质量优化；
- 真实订单、支付、物流或电商平台接入；
- 用户登录、角色权限和多租户；
- 生产安全、合规、风控、攻击防护和安全测试；
- 多 Agent、知识图谱、向量数据库和大规模 RAG；
- Redis、Kafka、Kubernetes、服务治理和高可用；
- 语音、图片、OCR 和多模态输入；
- 自动学习、强化学习或模型微调。

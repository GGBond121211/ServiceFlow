# 决策记录

## DEC-0001｜使用自建确定性模拟数据

- 日期：2026-08-09
- 状态：已接受
- 决策：订单、用户、商品、政策、退款、审批、工单和对话全部由仓库定义，不接真实企业后台。
- 原因：真实企业数据不可获得且涉及隐私；Agent 工程价值可以通过确定初始状态、工具副作用和最终状态评测证明。
- 权衡：业务复杂度低于真实系统，因此对外只称“模拟售后工作流”。

## DEC-0002｜V1 使用单 Agent 和确定性业务节点

- 日期：2026-08-09
- 状态：已接受
- 决策：使用一个 LangGraph Agent；语言理解和回复使用模型，政策和状态变更使用 Python 代码。
- 原因：CodeInsight 已展示多 Agent；本项目需要证明工具调用和普通业务落地，不需要再次堆叠角色。
- 权衡：不会展示多 Agent 协作，但系统更容易解释、评测和完成。

## DEC-0003｜不建设生产安全和防御性代码

- 日期：2026-08-09
- 状态：已接受
- 决策：V1 不实现账号鉴权、权限、风控、安全防护、安全测试、重试、熔断、缓存和复杂恢复。
- 原因：项目是本地学生作品集，无真实资金、用户和线上流量；这些内容会稀释核心业务和学习目标。
- 权衡：项目不能公开宣称可直接用于生产，也不能接入真实支付和客户数据。

## DEC-0004｜数据库采用渐进学习路径

- 日期：2026-08-09
- 状态：已接受
- 决策：领域和仓储先通过 SQLite 快速测试，再使用 SQLAlchemy 切换到 PostgreSQL；最终演示必须使用 PostgreSQL。
- 原因：降低首次学习数据库和 Agent 业务逻辑同时出现的认知负担。
- 权衡：需要保留一个 PostgreSQL 集成验证，避免只在 SQLite 上通过。

## DEC-0005｜Docker Compose 最终只包含两个服务

- 日期：2026-08-09
- 状态：已接受
- 决策：最终 Compose 只启动 FastAPI 和 PostgreSQL。前端使用静态文件服务器，不增加 Redis、Nginx、消息队列或 Kubernetes。
- 原因：两服务已经足以证明容器化和数据库联动，继续扩展没有当前用户价值。

## DEC-0006｜评测以数据库最终状态为主

- 日期：2026-08-09
- 状态：已接受
- 决策：评测主要检查任务决策、政策、工具和最终业务状态；自然语言只检查必要字段，不使用主观 LLM 总分作为主要结论。
- 原因：数据库状态可重复、可解释，能够防止模型只生成“已经完成”的文字。

## DEC-0007｜V1 使用原生浏览器前端

- 日期：2026-08-09
- 状态：已接受
- 决策：前端使用原生 HTML、CSS 和 JavaScript，通过 HTTP JSON 调用 FastAPI。
- 原因：项目招聘价值集中在 Agent 后端；额外前端框架会增加依赖和工期，却不改变核心证明。
- 复审条件：只有核心项目完成后，真实展示需求证明当前页面不足时才更换框架。
